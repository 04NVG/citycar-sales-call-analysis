# Анализ отдела продаж: агенты, которым можно доверять

**Демо:** https://citycar-sales-call-analysis.vercel.app

Работающий прототип к тестовому заданию CityCar (AI-оператор / AI-агент). Руководитель пишет: «Проанализируй работу отдела продаж за последние 30 дней». Система проходит весь путь: amoCRM и звонки → разбор звонков → метрики → отчёт → решения человека. Полный текстовый ответ на задание: [citycar_answer.md](citycar_answer.md).

Главный принцип: **LLM интерпретирует, код считает и проверяет, человек решает.**

## Что можно сделать в демо

**Анализ отдела** (`#report`). Команда руководителя запускает журнал работы агентов:

1. Orchestrator разбирает запрос.
2. CRM Sync и телефония поднимают данные.
3. Разборы звонков берутся из кэша.
4. Sales Analytics собирает fact pack.
5. Report Agent пишет текст.
6. Validator сверяет каждое число в этом тексте с fact pack.
7. Решения уходят руководителю.

В отчёте:
- KPI;
- наблюдения AI с кликабельными доказательствами;
- очередь решений для руководителя: утвердить, отложить или отклонить;
- таблица менеджеров с отклонениями от медианы;
- сделки под риском: нет задач, просрочка, «обещал в звонке, а задачи в CRM нет»;
- раздел «чего в отчёте нет и почему».

**Разбор звонка** (`#call`):
- таймлайн разговора, чат-транскрипт с подсвеченными цитатами и структурированный разбор;
- если изменить фразу в транскрипте, проверка цитат это заметит;
- если переключить «задача в CRM есть», маршрутизация на ревью пересчитается.

**Живой режим.** Нужен ключ Anthropic API: серверный (`ANTHROPIC_API_KEY`) или ключ посетителя (кнопка «Ключ API», хранится только во вкладке). С ключом модель разбирает ваш звонок и заново пишет отчёт, а валидатор проверяет его на месте.

Без ключа всё работает на сохранённых ответах модели. Проверки кода выполняются по-настоящему, прямо в браузере.

## Устройство

| Файл | Роль | Кто |
|---|---|---|
| `amo_leads_attention.py` | п. 3 задания: сделки без задач или с просрочкой через amoCRM API v4 (48 строк) | код |
| `sales_analytics.py` | Sales Analytics: метрики, аномалии, сделки под риском, связь «обещание ↔ задача» | код |
| `call_analysis.py` | Схема разбора звонка, проверка цитат, маршрутизация на ревью | код |
| `report_validator.py` | Validator: числа в тексте отчёта ⊂ fact pack, ссылки ведут на существующие сделки и звонки | код |
| `llm.py` | Call Analysis и Report Agent: Claude API, structured output по Pydantic-схемам | LLM |
| `transcript.py` | Транскрипт → сегменты (как после STT с диаризацией) | код |
| `scripts/build_demo_data.py` | Синтетический отдел: 4 менеджера, 90 сделок, звонки. Детерминированный seed | данные |
| `demo_samples.py`, `demo_report.py` | Сохранённые ответы модели для режима без ключа | данные |
| `api/index.py` | FastAPI на Vercel: `/api/analyze`, `/api/report`, `/api/health` | код |
| `public/` | Чистый HTML/CSS/JS. `index.html` — лендинг, `demo.html` — демо (логика проверок повторена в `app.js`). Старые ссылки `/#report`, `/#call`, `/#how` перенаправляются в демо | UI |
| `tests/` | 17 тестов: amoCRM на моках, схема, цитаты, аналитика, валидатор, API | |

Стек: Python 3.12, FastAPI, Pydantic, Anthropic SDK, pytest, Vercel.

## Запуск

```bash
pip install -r requirements-dev.txt
pytest -q
python scripts/build_demo_data.py   # пересобрать public/demo-data.json и проверить сохранённый отчёт
```

## Честно об ограничениях

- Данные синтетические: люди, клиенты, сделки и звонки выдуманы. STT по аудио, PostgreSQL, очереди и авторизация описаны в архитектуре, но в демо не реализованы.
- Код amoCRM сверен с документацией API v4 и проверен на моках. На реальном аккаунте его не запускали.
- Сохранённые ответы модели написаны Claude и проходят те же проверки, что и живые.
- Validator сверяет числа с множеством всех чисел fact pack. Число, которое случайно совпало с другим значением, он не поймает. Следующий шаг — ссылки «число → поле fact pack» в structured output.
- Лимит живых запросов на серверном ключе хранится в памяти инстанса. Ключ посетителя не сохраняется и не логируется.
