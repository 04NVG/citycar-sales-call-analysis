## 1. Архитектура

Принцип №1: LLM работает только с неструктурированными данными: речью, свободной формулировкой запроса руководителя и текстом отчёта. Выгрузку из API, связи между сущностями, просрочки и KPI считает обычный код. Поэтому цифры в отчёте воспроизводимы, а выводы AI можно проверить по первичным данным.

Принцип №2: звонки обрабатываются заранее, а не в момент запроса. Если транскрибировать записи за 30 дней по команде «проанализируй», ждать придётся десятки минут, а стоимость будет непредсказуемой. Поэтому контуров два: данные копятся непрерывно, а отчёт собирается по запросу из того, что уже обработано.

```
═ Контур 1. Ингест — непрерывно (webhooks + инкрементальный sync) ═════
 amoCRM API v4 ─────────────► CRM Sync                  [код]
 leads, tasks, events,         токен, ≤7 rps, upsert по id
 users, notes call_in/out             │
                                      ▼
 Телефония ─► Telephony Adapter ─► Call Ingest          [код]
 (провайдер    CDR + ссылки        запись → S3, sha256, связь
  CityCar)     на записи           звонок ↔ менеджер ↔ сделка
                                      │ Redis-очередь (retry, DLQ)
                                      ▼
                              STT + диаризация          [ML-сервис]
                                      ▼
                              Call Analysis             [LLM → JSON Schema]
                                      ▼
 PostgreSQL: raw JSON · сделки/задачи · звонки · транскрипты · анализы
 S3 (регион РФ): аудио, шифрование, автоудаление по lifecycle

═ Контур 2. Запрос руководителя ═══════════════════════════════════════
 РОП (Telegram / Web) ─► API (FastAPI): auth, RBAC, audit log
                              ▼
                       Orchestrator     [LLM: фраза → AnalysisRequest]
                              ▼         [код: workflow + delta-sync]
                       Sales Analytics  [код: SQL-метрики, аномалии]
                              ▼
                       Report Agent     [LLM: текст только из fact pack]
                              ▼
                       Validator        [код: числа и ссылки сверены]
                              ▼
                       Human Review ─► отчёт со ссылками на сделки/звонки
```

Что тут LLM, а что нет:

- **Orchestrator** (LLM + код). LLM только превращает фразу в структуру `{период, отдел/менеджеры, воронки}` и отвечает на уточняющие вопросы по уже посчитанным данным. Сам пайплайн фиксированный, так что «свободному» агенту здесь решать нечего.
- **CRM Sync** (код). Это обычная интеграция: `GET /api/v4/leads`, `/tasks`, `/events`, `/users`, `/leads/pipelines`. Изменения приходят через webhooks, а ночная сверка идёт по `filter[updated_at]`.
- **Telephony Adapter** (код). Провайдер телефонии CityCar мне неизвестен, поэтому интерфейс сделан общим: `list_calls(period)` и `get_recording(call_id)`. Если телефония уже интегрирована с amoCRM, первая реализация берёт данные из примечаний `call_in`/`call_out` (`params.link`, `duration`, `phone`, `uniq`). Иначе нужен адаптер к API провайдера, где есть журнал звонков и записи.
- **STT** (ML-сервис, не агент). Если запись стерео и менеджер с клиентом идут в разных каналах, диаризация по каналам ничего не стоит и точнее модельной.
- **Call Analysis** (LLM). Это единственное место, где без LLM не обойтись: нужно извлечь из разговора итог, следующий шаг и возражения по фиксированной схеме. Каждый звонок анализируется отдельным вызовом, без агентного цикла.
- **Sales Analytics** (код). KPI, сравнение менеджеров и аномалии (отклонение от медианы отдела) считаются на SQL и Python. LLM чисел не считает.
- **Report Agent** (LLM). Пишет сводку только из fact pack, то есть из метрик и id доказательств. Затем Validator проверяет, что каждое число из текста есть в fact pack, а каждая ссылка ведёт на существующую сделку или звонок.

Итого компонентов с LLM три, всё остальное — backend.

**Стек и надёжность.** Python/FastAPI, PostgreSQL (raw jsonb, нормализованные таблицы и анализы с версиями model/prompt/schema), S3-совместимое хранилище в РФ, Redis + Celery (Temporal подключается, только если появятся долгие workflow с ожиданием апрува), Docker. Идемпотентность обеспечивают upsert по id сделки/задачи и по `uniq` звонка, а результат анализа кешируется по ключу `(transcript_hash, prompt_version, model)`, поэтому повторный прогон не стоит денег. На 429/5xx срабатывает backoff, неудачные задачи уходят в DLQ, общий token bucket держит нагрузку ≤ 7 rps (лимит amoCRM на интеграцию). Для наблюдаемости: логи с `run_id`/`call_id`, OpenTelemetry → Grafana (лаг очереди, ошибки STT/LLM, доля невалидного JSON, стоимость прогона), Sentry. Расходы на LLM сдерживаются так: короткие звонки и автоответчики отсекаются до модели, ночная обработка идёт батчами, на каждый прогон задан лимит бюджета.

**Что происходит после команды «Проанализируй работу отдела продаж за 30 дней»:**

1. Период считается в часовом поясе аккаунта, проверяются права: РОП видит свой отдел, менеджер — только себя.
2. Делается delta-sync amoCRM, в отчёте фиксируется время снимка: «данные на 03.10, 09:00».
3. Сделки раскладываются на открытые, успешные (142) и проигранные (143), по стадиям и ответственным. Отдельно отмечаются сделки без открытых задач и сделки с просроченными задачами (`complete_till < now`, `is_completed = false`).
4. Звонки периода связываются с менеджером (справочник user_id ↔ добавочный) и со сделкой (через контакт или телефон). Несвязанные звонки идут в отдельную группу и не выбрасываются.
5. Если какие-то звонки ещё не прошли STT и анализ, они дообрабатываются.
6. Код считает метрики и аномалии по менеджерам и стадиям.
7. Источники сверяются между собой, и это самое ценное. Например, LLM нашла в звонке «договорились перезвонить в пятницу», а код видит, что задачи в CRM нет. Значит, конкретная сделка под риском.
8. Report Agent пишет отчёт, его проверяет Validator, а при срабатывании триггеров отчёт уходит человеку на ревью.

Отчёт разделён на четыре явно подписанных слоя:

| Слой | Пример | Откуда |
|---|---|---|
| Факты | «Открытых сделок без задач: N» + список ссылок | amoCRM, снимок на дату |
| Метрики | конверсия по стадиям, доля сделок с просрочкой, время от создания сделки до первого звонка | SQL, формула указана в отчёте |
| Интерпретация AI | «в 9 из 14 звонков менеджера X следующий шаг не согласован» + цитаты с таймкодами | Call Analysis, с пометкой AI |
| Рекомендации | «разобрать 5 сделок с просрочкой больше 7 дней» | черновик, утверждает РОП |

Если для KPI нет данных (план продаж, маржа), отчёт пишет «нет данных», а не оценивает на глаз. Покрытие показывается в каждом отчёте: «проанализировано K из M звонков, P% не связаны со сделками».

**Результат анализа звонка** (JSON Schema с проверкой через Pydantic; при невалидном ответе один повтор, затем DLQ):

```json
{
  "schema_version": "call_analysis.v1", "prompt_version": "…", "model": "…",
  "call_id": "…", "lead_id": 0, "manager_user_id": 0,
  "analyzable": true, "skip_reason": null,
  "call_type": "first_contact | follow_up | not_sales | voicemail",
  "customer_intent": {"value": "…", "confidence": 0.8, "evidence": ["e1"]},
  "outcome": {"value": "meeting_set | callback | thinking | refused | other", "confidence": 0.9, "evidence": ["e3"]},
  "next_step": {"agreed": true, "what": "…", "when_mentioned": "пятница", "evidence": ["e4"]},
  "qualification": {"need": "asked", "budget": "not_asked", "timeline": "asked", "decision_maker": "unclear"},
  "objections": [{"type": "price", "handled": "partially", "evidence": ["e2"]}],
  "script_checklist": [{"item": "…", "status": "done | missed | n/a", "evidence": ["e3"]}],
  "risks": [{"type": "promise_without_followup", "severity": "high", "evidence": ["e4"]}],
  "evidence": [{"id": "e4", "speaker": "manager", "start_sec": 182.4, "quote": "…"}],
  "needs_review": false, "review_reasons": []
}
```

Почему схема такая:
- Вместо свободного текста — enum, чтобы результаты можно было агрегировать по отделу.
- Каждый вывод ссылается на evidence с таймкодом. Код сверяет цитату с транскриптом и отправляет вывод на ревью, если совпадения нет.
- Модельный confidence откалиброван плохо, поэтому он нужен только для маршрутизации на ревью, а не как истина.
- Номера версий позволяют пересчитать результаты после смены промпта.
- Признак «задача в CRM есть или нет» модель не заполняет — его добавляет код при join.

## 2. Что система делает сама, а что передаёт человеку

| Сама (автоматически) | Решает или подтверждает человек |
|---|---|
| Сбор и нормализация данных amoCRM и телефонии | Справочник «менеджер ↔ добавочный», правила связи звонков со сделками |
| Транскрипция, классификация звонков, извлечение по схеме | Спорные интерпретации: низкий confidence, мало evidence, конфликт источников |
| Расчёт метрик, просрочек, аномалий | Любые выводы об эффективности конкретного сотрудника и кадровые решения |
| Черновик отчёта и рекомендаций, сверка чисел и ссылок | Серьёзные нарушения (грубость, обещания клиенту вне регламента) — только после прослушивания |
| Напоминание менеджеру о сделке без задачи (обратимо, по шаблону) | Изменения процессов и воронки, действия с клиентами, любые необратимые действия |

В CRM система ничего не пишет без явного включения, а каждое решение ревьюера логируется и потом используется для улучшения промптов.

**Три главных риска**

1. **Неполные или неверно связанные данные приводят к неверным выводам о людях.** Звонки с личных мобильных не попадают в телефонию, задачи ведутся не всеми, звонок привязан к контакту, а не к сделке. Отчёт тогда уверенно обвинит не того. *Что делаем:* показываем метрики покрытия в каждом отчёте, держим группу «не сопоставлено», ведём ручной справочник связей, задаём порог покрытия, ниже которого выводы по менеджеру не формируются.
2. **Ошибки STT или LLM влияют на оценку сотрудников.** Из-за шума, обрывков или перепутанных спикеров получается «менеджер не назвал цену». *Что делаем:* только структурированный вывод с обязательными evidence, проверка цитат, факты отделены от интерпретаций. Плюс golden set из 50–100 звонков, размеченных РОПом: на нём проверяется каждая смена модели или промпта. Автоматических кадровых выводов нет.
3. **Персональные данные и записи разговоров (152-ФЗ).** В записях есть голос, телефоны, иногда паспортные и финансовые данные. *Что делаем:* храним данные в РФ, STT/LLM выбираем с учётом локализации и трансграничной передачи (российский провайдер или self-hosted модель; для внешнего LLM — маскирование телефонов и номеров до отправки плюс решение юриста). Доступ по RBAC, шифрование, журнал доступа к записям. Аудио автоматически удаляется через N дней, транскрипты хранятся по политике, агрегаты — бессрочно.

Ограничение, которое надо учитывать: лимит amoCRM 7 rps на интеграцию. Первая выгрузка большого аккаунта займёт заметное время, поэтому дальше работаем только инкрементально и через webhooks.

## 3. Код: сделки без открытых задач или с просроченными задачами (Python, 48 строк)

```python
import os, time, requests

BASE = f"https://{os.environ['AMO_SUBDOMAIN']}.amocrm.ru/api/v4"
S = requests.Session()
S.headers["Authorization"] = f"Bearer {os.environ['AMO_TOKEN']}"  # долгосрочный или OAuth access token
CLOSED = {142, 143}  # системные статусы: «Успешно реализовано» / «Закрыто и не реализовано»

def fetch_all(path: str, key: str, params: dict):
    """Обход пагинации amoCRM v4: limit<=250, page=1..N, пока в ответе есть _links.next."""
    page = 1
    while True:
        for attempt in range(5):
            r = S.get(f"{BASE}/{path}", params={**params, "limit": 250, "page": page}, timeout=30)
            if r.status_code != 429:            # лимит: 7 запросов/сек на интеграцию
                break
            time.sleep(2 ** attempt)
        if r.status_code == 204:                # пустая выборка — тела нет
            return
        r.raise_for_status()
        data = r.json()
        yield from data["_embedded"][key]
        if "next" not in data.get("_links", {}):
            return
        page += 1
        time.sleep(0.2)                         # держимся ниже лимита

def leads_needing_attention(pipeline_id: int | None = None) -> list[dict]:
    now = int(time.time())
    lead_filter = {"filter[pipeline_id]": pipeline_id} if pipeline_id else {}
    leads = [l for l in fetch_all("leads", "leads", lead_filter) if l["status_id"] not in CLOSED]
    # Задачи не вложены в сделку: берём все открытые задачи по сделкам и группируем по entity_id
    deadlines: dict[int, list[int]] = {}
    for t in fetch_all("tasks", "tasks", {"filter[is_completed]": 0, "filter[entity_type]": "leads"}):
        deadlines.setdefault(t["entity_id"], []).append(t["complete_till"])
    result = []
    for lead in leads:
        dl = deadlines.get(lead["id"], [])
        overdue = [d for d in dl if d < now]    # complete_till — unix timestamp (UTC)
        if dl and not overdue:
            continue
        result.append({
            "lead_id": lead["id"], "name": lead["name"], "status_id": lead["status_id"],
            "responsible_user_id": lead["responsible_user_id"],
            "problem": "overdue_tasks" if overdue else "no_open_tasks",
            "overdue_count": len(overdue),
            "max_overdue_hours": round((now - min(overdue)) / 3600, 1) if overdue else None,
        })
    return sorted(result, key=lambda x: -(x["max_overdue_hours"] or 0))
```

- **Доступ.** Нужны поддомен аккаунта и токен. Подходит долгосрочный токен приватной интеграции (срок от 1 дня до 5 лет, без refresh) или OAuth access token (живёт 24 часа; refresh token одноразовый и действует 3 месяца, поэтому в проде его надо сразу сохранять после обмена). Запросы идут с правами пользователя, установившего интеграцию, так что ему нужен доступ ко всем сделкам отдела.
- **Почему несколько запросов.** В ответе `/leads` задач нет. Поэтому код отдельно выгружает открытые задачи (`filter[is_completed]=0`, `filter[entity_type]=leads`) и связывает их со сделками через `entity_id`. Пагинация: `limit` до 250, `page` увеличивается, пока в ответе есть `_links.next`. Пустая выборка обрабатывается и как 204, и как пустой `_embedded`.
- **Просрочка.** Задача открыта, а `complete_till < now` (unix time, сравнение в UTC). «Без задач» здесь значит «без открытых задач», потому что выполненные задачи не считаются. В модели сделки есть поле `closest_task_at`, но его точная семантика в документации не описана, поэтому расчёт идёт по самим задачам.
- **Что нужно для продакшена.** Выгрузка не каждый раз целиком, а инкрементальный sync в PostgreSQL по `updated_at` с webhooks. Общий rate limiter на все воркеры, retry на 5xx, обновление OAuth-токена. Отдельно стоит решить с бизнесом, учитывать ли задачи, поставленные на контакт сделки: менеджеры часто ставят их туда. Плюс тесты на моках API.

Репозиторий: https://github.com/04NVG/citycar-sales-call-analysis. Там этот код с тестами (пагинация, 429, 204, исключение закрытых статусов) и `call_analysis.py`: Pydantic-схема анализа звонка с проверками из п. 1. Код сверяет цитаты с транскриптом и ищет случаи «следующий шаг согласован, а задачи в CRM нет».

## 4. AI-проект

**Анализ отдела продаж: прототип этой архитектуры.**
Демо: https://citycar-sales-call-analysis.vercel.app · код: https://github.com/04NVG/citycar-sales-call-analysis

**Задача.** Показать на работающем коде архитектуру из п. 1. Команда «Проанализируй работу отдела продаж за 30 дней» проходит путь: данные CRM и звонков → разбор звонков → метрики → отчёт → решения руководителя. LLM интерпретирует, код считает и проверяет, человек решает.

**Как устроено.**
- Разбор звонка: Claude API, structured output по Pydantic-схеме, каждый вывод ссылается на цитату с таймкодом. Код сверяет цитаты с транскриптом и находит «договорились в звонке, а задачи в CRM нет».
- Метрики и аномалии по менеджерам считает код (fact pack).
- Report Agent пишет текст только по fact pack, Validator сверяет каждое число и ссылку.
- Рекомендации попадают в очередь решений руководителя.
- В интерфейсе видно, что сделала модель, а что код. Есть живой режим по ключу API.

**Стек.** Python, FastAPI, Pydantic, Anthropic SDK (structured outputs), pytest, Vercel; фронтенд на HTML/CSS/JS без фреймворков.

**Результат.** Работающее демо на синтетическом отделе: 4 менеджера, 90 сделок, около 140 звонков за период. 17 автотестов: amoCRM на моках, схема, проверка цитат, аналитика, валидатор, API.

**Честно о контексте.** Проект собран за время выполнения этого задания с помощью AI-ассистента для кода (Claude Code). Данные синтетические, реальных пользователей и бизнес-метрик нет: это демонстрация подхода, а не продакшен.
